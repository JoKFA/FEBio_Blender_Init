# 08 开发规范

给谁看：所有参与开发的人，包括 AI 开发会话，和审查者。读完能知道：代码和文档放哪、怎么开发和提交、怎么检查、什么叫"完成"。不包括：设计本身（见 04、05）。规范的目的只有一个：**几个人同时开发时，代码不乱、结果可信、谁都能接手。**

## 1. 仓库结构

```
asrp/
  src/asrp_core/        核心程序（计算、文件格式、命令行）。不能 import bpy
  blender_addon/        Blender 插件（只管界面）。不能用第三方库
  tests/                自动测试
  tools/                检查、分析、渲染用的小工具（不是产品代码）
  docs/                 设计文档（本目录）
  assets/  runs/        实验室原始场景、运行结果 —— 被 git 忽略
  data/                 导出和派生数据 —— lab_export、preview、tetmesh 提交，其余忽略（ADR-19）
```

逐个文件夹、主要文件的说明见 [README](README.md) 的"仓库目录"。新功能放进哪个目录，以 [04 系统设计](04-architecture.md) 第 3 节为准。拿不准时先问，不要自己新建顶层目录。

**什么进仓库**：仓库放项目本身，不放开发过程。进仓库的是产品代码、测试、检查和导出工具（`tools/`）、设计文档，以及 `data/` 里提交的几个文件夹（ADR-19）。**一次性脚本和带日期的工作计划不进仓库**：一次性脚本（只为一次测量或一趟上机写的）放在数据旁边，仓库外；工作计划写进 09 的任务卡或 13 的解释，不单独存文件。

## 2. 开发环境

| 东西 | 版本 | 说明 |
|---|---|---|
| 操作系统 | Windows 11 | 第一阶段只保证 Windows |
| Python | 3.13 | 和 Blender 5.2 自带的版本一致 |
| 包管理 | uv | `uv sync` 安装依赖，`uv run ...` 运行 |
| Blender | 5.2.x LTS | |
| FEBio | 4.13.0（随 FEBio Studio 安装） | 官网注册后下载；**安装包不能放进仓库，也不能转发给别人**（许可规定） |
| 路径 | 只用英文字母和数字 | FEBio 可能打不开中文路径 |

装好以后运行 `uv run asrp doctor`，四项都显示 `ok` 才算环境就绪。

## 3. 分支和合并

- `main` 分支**永远是能用的状态**：自动检查全部通过。
- 每个任务开一个新分支，名字用任务编号加简短描述，例如 `t-06-febio-scene`。
- 一个合并请求只做一个任务。太大就拆。合并请求的内容超过大约 400 行（不含测试数据），要先和审查者商量能不能拆。
- 合并之前：先把最新的 `main` 合进自己的分支，自动检查通过，至少一个人审查通过。
- 不允许直接往 `main` 推代码，也不允许强制推送覆盖 `main`。
- **远程仓库**：GitHub 私有仓库 `JoKFA/FEBio_Blender_Init`（ADR-14）。每个任务在自己的分支上开发，推送后在 GitHub 上开合并请求（GitHub 叫 Pull Request），审查通过后再合并。
- 分支保护是否开启见 09 的 T-16。不管开没开，规矩不变：**不许直接推，一律走合并请求**。

## 4. 提交信息

- 第一行用一句话说明**为什么**改，而不是只说改了什么。
- 正文写清楚背景、做法和证据（关键的测试或运行输出）。
- 写明任务编号，比如 `T-06a`。
- 用自己的名字和邮箱提交。**不在提交信息里加 AI 署名**（项目负责人的要求）。
- 不提交密码、密钥、个人数据、实验室的原始场景文件、论文或运行结果。

## 5. 写代码的规矩

1. **核心程序不碰 Blender，插件不做计算。** 违反这条的合并请求一律退回。
2. **单位只在导入时换算一次**，之后全部用毫米、牛顿、兆帕、秒。变量名或注释里写清单位，比如 `stiffness_mpa`。
3. **不加没被要求的功能。** 任务卡没写的就不做；觉得应该做，就写进 [11](11-risks-and-questions.md) 或者提给项目负责人。
4. **三段相似的代码，好过一个过早的抽象。** 真的出现第四次再提炼。
5. **错误信息说人话**，并且说清楚怎么办：写"找不到 FEBio。请安装 FEBio Studio，或设置 ASRP_FEBIO 指向 febio4.exe"，不要写 "FileNotFoundError"。
6. **注释解释"为什么"**，不要复述代码在做什么。坑和反直觉的地方一定要写注释，比如重力反号。
7. **新增依赖要说明理由**，写在合并请求里，用 `uv add` 添加。插件不能有第三方依赖，因为 Blender 自带的 Python 装不了。
8. 代码风格：用 ruff 检查。`ruff check`，规则 E、F、I、UP、B，是 `tools/verify.py` 的第一步，以工具检查结果为准。规则的例外：
   1. **行宽不检查**（E501 忽略）：现有代码写在约 150 列，全部重排会把真正的改动埋掉；
   2. **不加 `ruff format --check`**，原因同上。下次整个重写某个文件时再回头看；
   3. **规则 B905（`zip()` 不带 `strict=`）整个仓库忽略**：`zip()` 都是把一起造出来的序列配对，加 `strict=` 只会添噪音；
   4. **两个由 Maya 自带的 Python 运行的脚本**（`tools/maya_export.py`、`tools/ziva_machine_export.py`）在 `pyproject.toml` 里各关了几条规则（老式字符串格式化和三条风格规则），保持原样。具体清单只看 `pyproject.toml`，这里不抄。

## 6. 测试的规矩

1. **每个新行为都要有测试**，修 bug 要先写一个能复现这个 bug 的测试。
2. **测试必须真的能失败。** 断言"数量大于 0、误差小于 X"，而不是只断言"返回了东西"。合并请求里要说明：如果代码写错了，哪个测试会失败。
3. 测试数据用小的、合成的例子（比如几个四面体），放在 `tests/` 里。
4. 需要实验室资产的测试，在没有资产的电脑上要自动跳过，并说明原因；**发布前必须在有资产的电脑上跑一遍**。
5. 测试不能往仓库目录里写文件，临时文件一律写进临时目录。
6. **自动检查**是"能合并"的最低要求。在仓库根目录运行：

   ```bash
   uv run python tools/verify.py
   ```

   不带参数就是全量，是"能合并"的定义：`ruff check`（第一步）、不许实验室和厂商文件进 git 的检查、全部测试（含真实嘴唇的慢测试）、`asrp doctor`、Blender 官方的插件 manifest 校验、Blender 插件检查、回放检查、面板检查，任何一步失败就停下并报错。它用和 `asrp doctor` 一样的方法找 Blender，所以在任何装好环境的电脑上都能跑。

   开发过程中不必每一步都跑全量，分三级，后一级包含前一级：

   | 级 | 跑什么 | 大约多久 | 什么时候用 |
   |---|---|---|---|
   | `--level docs` | 排版检查、防误提交检查、文档和验证门自己的测试 | 10 秒 | 只改了文档 |
   | `--level core` | 加上全部单元测试（不含真实嘴唇的慢测试） | 3 分钟 | 改了代码或测试 |
   | 不带参数（`full`） | 加上慢测试、`asrp doctor` 和 Blender 的四项 | 6 分钟以上 | 提合并请求之前；改了 `blender_addon/` |

   只改文档时跑的 docs 级，会拿结果页（15）和存下的报告对数，但不拿文档去对仓库外的实验室数据：`tests/test_lab_facts.py` 只在 core 和 full 两级里跑。所以改了文档里关于实验室的数字，要再跑一次 core 级。

   **只属于一台机器的东西不进仓库**：本机的文件夹位置、只有一个人用得上的数据和脚本，都不提交。仓库外的数据在本机的哪里，写在仓库根目录的 `.local/` 里（`ziva_trip_pointer.json`、`paths.json`）或环境变量 `ASRP_ZIVA_TRIP`、`ASRP_LAB_DATA` 里，由 `tools/local_paths.py` 读；`.local/` 被 git 忽略。代码、测试和文档里不写本机的绝对路径，要举例就用编出来的路径。验证门的第二步（`tools/check_no_lab_files.py`）会拦：`.local/` 下的文件被跟踪、任何被跟踪的文本文件里出现这个仓库所在的文件夹或当前用户的主目录，都算失败。没有配置位置的机器上，用到仓库外数据的测试会跳过并打印 `NOT VERIFIED`。

   **关于实验室的事实要有会失败的检查**：实验室的训练、Ziva 的结果和设置这类关键事实，写进文档之前先在 `tests/test_lab_facts.py` 里加一条能失败的检查（数据在仓库外，没有数据时跳过并打印 `NOT VERIFIED`）。写数字时写明哪一次运行、哪些顶点、哪一帧对哪一帧、最大还是平均。实验室自己存下了某个状态的结果时，直接和它比，不用别的实验去拼（[13](13-explanations.md) E-15）。

   `--level auto`（`uv run python tools/verify.py --level auto`）按未提交的文件和最近一次提交的文件自己选级。每台机器可以在自己的本机设置里（不进仓库，`AGENTS.md`、`CLAUDE.md` 和 `.claude/` 都是各机自己的，验证门拒绝它们被跟踪）让开发工具每一轮结束时调用它。它不能代替合并前的全量。

## 7. 什么叫"完成"

一个任务只有同时满足下面所有条件，才能说"完成"：

- [ ] 任务卡上的每一条验收标准都满足了，并且附上证据：**真实命令和它的真实输出**，不是"测试应该能过"；
- [ ] 通过**真正的入口**运行过一次（命令行或者 Blender 按钮），用的是真实形状的数据，包括空值、缺字段这些情况；
- [ ] `uv run python tools/verify.py` 全部通过；
- [ ] 新行为有测试，而且测试能失败；
- [ ] 受影响的文档已经更新（见第 9 节）；
- [ ] 至少一个人审查通过。

"测试全绿"本身**不等于**完成。

## 8. 审查

审查者对照任务卡和这份规范检查：

| 检查什么 | 问自己 |
|---|---|
| 范围 | 做的是不是任务卡要求的？有没有多做？ |
| 正确性 | 证据能不能说明它真的工作？测试能不能失败？ |
| 设计 | 有没有违反第 5 节的规矩？有没有偏离 04/05 的设计？ |
| 单位和坐标 | 换算是不是只做了一次？有没有写清楚单位？ |
| 文档 | 该更新的文档更新了吗？ |

- 影响正确性和需求的问题必须改；纯风格问题提一下就行，不阻止合并。
- 可以用 AI 做第二意见的审查（另一个模型更好），但最终是否合并，由人决定。

## 9. 文档的规矩

| 发生了什么 | 更新哪份文档 |
|---|---|
| 做了一个设计决定 | [10 决策记录](10-decisions.md) 加一条，并更新它最前面的"现在生效的是什么" |
| 发现设计要改 | 先改 04/05 并经过审查，再改代码 |
| 完成一个试验 | 05 的状态列、11 的假设台账 |
| 发现新的坑 | 05 第 5 节，并加一个对应的测试 |
| 实验室回答了问题 | 11 的问题清单，以及受影响的文档 |
| 任务完成或取消 | 09 里任务卡的状态；然后把整张卡原样搬到 [archive/09-completed-tasks.md](archive/09-completed-tasks.md)，09 第 5 节的索引加一行 |
| 回答了一个"为什么"的问题（要翻好几份文档才拼得出答案） | [13 设计解释](13-explanations.md) 加一条，相关文档链过去 |
| 设计变了，13 里的解释跟着过时 | 改掉那一条；或者在标题后标"已过时，见 ADR-xx"，整条搬到 [archive/13-audit-history.md](archive/13-audit-history.md)，13 的目录里留一行指过去 |
| 做了一次审计，或某一天的逐项核对 | 记录直接写进 [archive/13-audit-history.md](archive/13-audit-history.md)（编号照常取 `E-xx`，13 的目录加一行指过去）；它改变的事实写进各自的文档 |

文档里出现的实测数字，要写明是哪个命令或脚本得出的。

## 10. 数据和安全

- 实验室的原始场景文件（`assets/`）、论文、演示视频、实验室的控制器源码和运行结果（`runs/`）**永远不进 git**。`data/` 里的 `lab_export/`、`preview/`、`tetmesh/` 提交到私有仓库，其余不提交（ADR-19）。这些都不发到仓库以外的地方。实验室源码只读，用 `git show` 查，不运行（ADR-28）。
- **被哈希的文件按字节检出**：`data/` 和 `tests/fixtures/` 下的文件由 sha256 识别（`scene.json`、`data/tetmesh/lips.json` 和 S1 示例都记着哈希）。Git for Windows 默认 `core.autocrlf=true`，会在检出时改换行符，哈希就全对不上。仓库根目录的 `.gitattributes` 把这两个目录设成 `-text`，检出的字节等于仓库里的字节，不管各人怎么设。往这两个目录加新的文本文件时不用另外处理；要在别的目录放被哈希的文件，先把目录加进 `.gitattributes`。验证办法：用 `git clone --config core.autocrlf=true` 克隆，跑 `tests/test_scene.py`、`test_asset.py`、`test_tetmesh.py`、`test_trajectory.py`，应全部通过。
- 实验室的论文还在审稿，不对外引用其中的内容和图表。
- FEBio 的安装包和程序文件不能放进仓库，也不能转发（许可规定）。每个人自己去官网下载。
- FEBio 启动时会向犹他大学发送一个匿名编号，用于统计使用情况（许可协议里写明了）。除此之外，软件不联网。
- 不在代码或配置里写任何密码、密钥。

## 11. 和 AI 开发会话合作

AI 开发会话和人一样遵守本规范，另外：

1. **一个会话只做一张任务卡。** 交给它的说明就是任务卡本身，再加一句"先按 docs/README.md 的'先读哪几份'读开发者起步文档，再只读这张任务卡点名的文档和章节，不要通读全部文档"。
2. 会话必须交出证据：真实命令和输出，以及改动的文件清单。
3. 会话**不能自己改设计**。发现设计有问题，要停下来报告，由项目负责人决定。
4. 对任务卡有疑问，先查 [13 设计解释](13-explanations.md) 的目录，只读对上的那一条；查不到再问。
5. 会话产出的合并请求，和人写的一样要经过审查。

## 12. 版本

- 版本号写在 `pyproject.toml` 和插件的 `blender_manifest.toml` 里，两处保持一致。
- 第一阶段用 `0.x`。每完成一个里程碑（见 09），版本号加 0.1，并在 git 上打标签。
