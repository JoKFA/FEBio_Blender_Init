# 04 系统设计

这份文档说明软件分成哪几块、每块负责什么、数据怎么在它们之间流动。目标是：任何一个开发者只看这份文档和自己的任务卡，就知道自己写的东西放在哪、要和谁对接。

## 1. 总体结构

```
┌──────────────────── Blender ────────────────────┐
│  ASRP 插件（只管界面）                           │
│  导入资产 · 检查设置 · 运行 · 回放 · 对比          │
└───────────────┬─────────────────────▲───────────┘
                │ 调用命令行，传文件夹路径 │ 读取结果文件
                ▼                     │
┌──────────── asrp_core（独立程序）─────┴──────────┐
│  资产导入 → 场景描述 → 四面体化 → 生成 FEBio 输入   │
│  → 调用 FEBio → 读结果 → landmark 变形层          │
│  → 回放包 · 对比报告 · 溯源记录                   │
└───────────────┬─────────────────────▲───────────┘
                │ .feb 输入文件          │ 日志和结果
                ▼                     │
            ┌────────── FEBio ──────────┐
            │  有限元求解（不改它的代码）  │
            └───────────────────────────┘

所有输入、中间文件、结果都落在一个"运行文件夹"里。
```

三条基本原则：

1. **Blender 只管界面。** 插件里不写任何计算逻辑。插件崩了或者以后换成别的界面，计算部分完全不受影响。
2. **核心程序不依赖 Blender。** 可以单独在命令行里运行，以后实验室的控制器也通过它来调用物理计算。
3. **模块之间只通过文件交换数据。** 每一步的输入、输出都能单独打开检查，出了问题能定位到具体哪一步。

## 2. 两段计算

根据[资产分析](03-asset.md)第 4 节（实验室源码确认了没有别的路，ADR-29），最终的嘴唇形状由两段计算叠加而成，系统也按这两段来设计：

| 段 | 做什么 | 由谁算 | 输入 | 输出 |
|---|---|---|---|---|
| **物理段** | 下颌带动嘴唇，加上重力、惯性、组织之间的粘连 | FEBio | 场景描述 + 骨头的运动（landmark 不进物理，进物理的只有下颌这类骨头运动） | 每帧"只有物理"的嘴唇形状；其中**第 14 帧沉降后的形状**单独交出，它是控制器优化的起点（ADR-30）；每帧每块组织的应变能，只作诊断输出（ADR-33） |
| **landmark 段** | 300 个 landmark 的蒙皮变形叠加在物理结果上 | 我们自己的代码（纯几何，不需要 FEBio） | 物理段的结果 + landmark 运动 + 蒙皮权重 | 每帧最终的嘴唇形状 |

分成两段的好处：和 Ziva 对比时，可以先单独比较物理段。差异出在物理还是出在 landmark 层，一眼就能看出来。

landmark 段是物理之后的**可替换层**：顺序按实验室源码和论文 Algorithm 2 的第 12、13 步（先在物理模拟器开着的情况下把优化出的控制量作用到枢轴，再由 landmark 经 LBS 公式给出最终轨迹，ADR-29）。所以以后若要加一个"landmark 进物理"的模式，只是多一种输入，不用重建（第二阶段，现在不做；演示里有人复述的顺序和这里相反，见 11 的 Q21）。

## 4. 运行文件夹

每次运行一个文件夹，放在 `runs/<运行编号>/` 下面，**里面的东西足以独立重现这次运行**：

```
runs/2026-11-03_neutral-to-AA_001/
  scene.json          场景描述（这次用到的全部设置）
  trajectory.json     这次的运动（每个驱动源每帧的刚体变换、landmark 每帧的平移）
  meshes/             用到的网格（毫米、Z 轴朝上），包括已落盘的四面体网格（只读，哈希记在 provenance.json）
  landmarks/          场景引用的 landmark 蒙皮权重（原样拷贝）
  model.feb           生成的 FEBio 输入
  model.log           FEBio 日志（包含每帧节点位置）
  physics/            物理段结果（含第 14 帧沉降后的形状、每帧每块组织的应变能）
  final/              叠加 landmark 段之后的结果
  playback.json       回放包（Blender 加载用）
  playback.pc2
  run_report.json     运行报告：临时值和来源、没建的粘连、生成器报告、合理性检查、用时
  compare/            和 Ziva 对比的报告（如果做了对比）
  provenance.json     溯源记录
```

`asrp run <scene.json> <trajectory.json>`（T-06a，`simulate.py`）现在写出：场景文件夹里场景引用的每个文件按原来的相对路径拷进来（所以运行文件夹里的 `scene.json` 能直接再跑），运动改名为 `trajectory.json`；`physics/positions.json`（外壳写的，FEBio 的全部计算点，只有第 1 到 N−1 帧，坑 15）；`physics/display.json`（显示网格每帧的位置，第 0 帧是静止姿态，`asrp-display/1`）；`physics/settled_frame14.json`（第 14 帧的计算点和显示网格）和 `physics/settled_frame14.obj`（第 14 帧的显示网格，带面）；回放包是显示网格本身（嘴唇 10,240 个顶点，不是四面体网格的表面，`node_ids` 为 null）；`run_report.json`。还没有的：`final/`（T-09）、应变能（T-06b）、`compare/`（T-11）。FEBio 失败或取消时只写 `run_report.json`（检查 (a) 不通过），不写任何结果。生成器拒绝的场景（检查有错、显示顶点离四面体太远、一个点被两个刚体要走……）不建运行文件夹，`asrp run` 打印原因和 `run NOT STARTED`。

`runs/` 不进 git。`data/` 里提交的有 `lab_export/`、`preview/`、`briefing/`、`tetmesh/`（四面体网格是只读输入，ADR-19、ADR-20），其余不进。四面体网格是**显式生成一次、落盘并记哈希的输入**，运行时只读，不在运行中重新生成（fTetWild 同输入多次运行结果不同，见 ADR-20 和 [13](13-explanations.md) E-03）。需要分享某次运行时，把整个文件夹打包发送。

替身模式（T-08）的运行文件夹只有 `model.feb`、`model.log`、`physics/positions.json`（每帧每个节点的位置，几何毫米：已除以 k，ADR-36）、`provenance.json`，FEBio 的 `.xplt` 运行结束后删掉；失败和取消的运行没有 `physics/`；`provenance.json` 里不写任何本机绝对路径，输入按文件夹内的名字记哈希，所以整个文件夹复制到别处也能原样重跑。

## 5. 主要文件的内容

格式细节（字段名、类型）写在代码的格式说明里：`src/asrp_core/scene.py`、`src/asrp_core/trajectory.py` 开头（T-05 定稿）。这里只规定**必须包含的信息**。

两条通用规则：
- **大数组不内嵌。** 网格、四面体网格、landmark 蒙皮权重都是被引用的文件，`scene.json` 里只写路径和 sha256。场景文件因此能用眼睛读，文件被改过也一查哈希就知道。例外是粘连权重：它是稀疏列表，直接写在 `scene.json` 里；单个粘连超过一万项时再改成引用文件（ADR-34）。
- **校验结果分"错误"和"提醒"。** 错误是算不了或会算错（缺文件、哈希不符、连接没有有效顶点……），`asrp check` 失败；提醒是能算、但缺了要补的东西（比如软组织还没有任何连接），`asrp check` 照样通过，提醒要写进导入的检查报告。

### 5.1 场景描述 `scene.json`

| 部分 | 必须包含 |
|---|---|
| 单位 | 固定为 mm、N、MPa、s；记录每个网格原来的变换、从原始资产换算过来的系数和坐标轴转换（顺序见 [03](03-asset.md) 第 10 节）。**几何单位和物理尺度分开**（ADR-22）：`units.mm_per_scene_unit`（几何，0.962，**必填**）；`units.physics_length_scale`（无量纲 k，**可以不写**，不写时取 1.0 并把来源标成"我们定的"；第一阶段按真人大小取 0.67，由导入写进场景，T-06a 实现，ADR-31）：求解器把模型当成几何尺寸的 k 倍大来算，几何和输出仍是毫米；实现是 FEBio 里节点坐标 = 几何毫米 × k、物理参数不缩放、读回除以 k（[05](05-ziva-to-febio.md) 第 2 节，ADR-36） |
| 软组织 | 名字、网格文件、原始 OBJ 的文件名和 sha256、四面体网格文件及其内容哈希、材料（类型和参数）、每个参数的来源（实验室设置 / Ziva 默认值 / 我们定的） |
| 骨头 | 名字、网格文件、原始 OBJ 的文件名和 sha256、质量、运动方式：**"固定"或"给定"**（ADR-21）。给定时写明**跟随哪个驱动源**，运动由 `trajectory.json` 里这个驱动源的每帧变换提供 |
| 驱动源 | 名字（实验室资产里就是关节名，比如 `jaw01`），以及可选的铰链说明（枢轴、转轴），用来生成代用运动和做检查。一个驱动源可以带动几块骨头：下颌和下牙都跟随 `jaw01`，和 Maya 里一个关节同时带动两块骨头一样（[03](03-asset.md) 第 4 节）。**派生驱动源**（T-06a 补充，见本节末的"嘴角的锚"）：可以不带自己的运动，写成"驱动源 X 的 factor 倍"，由 X 的运动算出来 |
| 连接 | 连接的两样东西、每个顶点的权重（稀疏列表 `[[顶点, 权重], ...]`）、刚度、类型。类型是 [05](05-ziva-to-febio.md) 第 3 节的两种做法：硬绑定（`hard`，没有刚度）或弹簧（`spring`，刚度 × 权重）。第一阶段：上唇 `hard`、下唇 `spring`、嘴角 `spring` 连到"锚"（05 第 3 节，ADR-32）。粘连顶点怎么对应到计算点见 05 第 3 节。`to` 可以是骨头，也可以是下面的锚 |
| 锚 | 可选。名字，以及它跟随哪个驱动源（`anchors` 一节，见本节末）。锚是不显示、不参与碰撞、没有网格的刚体 |
| landmark | 名字、静止位置、对嘴唇顶点的蒙皮权重（被引用的文件；里面的矩阵导入时换算成毫米、Z 轴朝上，T-09） |
| 求解设置 | 帧率、每帧子步数、阻尼、重力、分析类型（动力学）。场景不记帧数：运动的帧率必须等于这里的帧率，帧数由 `trajectory.json` 给出 |
| 来源 | 从哪个资产文件、哪次导出生成的 |

**嘴角的锚（T-06a，05 第 3 节，ADR-32、ADR-36）。** 格式仍是 `asrp-scene/1`：只加了两个可选字段，旧文件原样可读，没有这两个字段的场景写出来也和以前逐字节相同，所以不升版本号。

```
"drivers": [
  {"name": "jaw01", "hinge": {...}},                              # 有自己的运动（trajectory.json 里有）
  {"name": "lip_corner_blend", "hinge": null,                     # 派生：trajectory.json 里不写它
   "blend": {"of": "jaw01",                                       #   从哪个驱动源派生
             "factor": {"value": 0.5, "source": "ours", "note": "..."}}}   #   α，范围 [0, 1]
],
"anchors": [                                                      # 可选，缺省为空
  {"name": "lip_corner_anchor", "driver": "lip_corner_blend", "note": "..."}
]
```

- **派生驱动源 `blend`**：`of` 必须是另一个驱动源，而且那个驱动源要有铰链（`hinge`），也不能自己再是派生的（不连环）。它的每帧变换 = 绕 `of` 的**同一个铰链**（同一个枢轴、同一个转轴）转 `factor` × `of` 那一帧的转角。α = 0 恒为单位变换（和颅骨重合），α = 1 等于 `of` 本身，α = 0.5 就转一半。`of` 的变换里不在铰链上的部分（离轴转动、平移）这个版本丢掉，只取绕铰链轴的有符号转角。以后 `of` 不是纯铰链时，派生改用旋转插值（旋转部分按 α 球面插值，平移按 α 线性插值），到时在这里补，现在不支持，写了就报错。`blend` 和 `hinge` 不能同时有；`blend` 的驱动源 trajectory.json 里不用写运动，写了会被忽略（提醒）。
- **锚 `anchors`**：静止时和颅骨重合（静止位置 = 世界坐标原样，没有自己的位置字段），每帧的变换就是它跟随的那个驱动源（通常是派生的）的变换。没有网格、没有质量、不参与碰撞，所以不画、也没有源 OBJ。连接的 `to` 可以写锚的名字。锚的名字不能和骨头、软组织重名；`driver` 必须是场景里列出的驱动源。左右两个嘴角共用同一个锚（两边绕同一个铰链转同样的角度）。
- **连接的三样东西**不变：类型 `hard` / `spring`（`hard` 的 `stiffness.value` 必须是 `null`，`spring` 必须有数）、每个顶点的权重、目标（颅骨、下颌或锚）；`spring` 的基础刚度和其他参数一样带来源。
- **检查**（都是错误）：锚或派生驱动源指向不存在的驱动源；α 不在 [0, 1]；派生驱动源的 `of` 没有铰链或自己也是派生的；`spring` 没有刚度；`hard` 带了刚度。
- 生成器（T-06a 的 B2）把驱动源的运动解出来用 `asrp_core.scene.driver_motion(scene, trajectory)`：返回每个驱动源（含派生的）每帧的 4×4 变换。

### 5.2 运动 `trajectory.json`
- 每个驱动源，每一帧的 **4×4 刚体变换**（毫米、Z 轴朝上，包含平移和旋转，ADR-21；**列向量约定**，Maya 是行向量约定，转换时要转置，ADR-34），以驱动源的名字为键。跟随同一个驱动源的骨头都用这一份变换。骨头可平移也可旋转（论文 4.1.3），甩头实验里整个头在平移（4.4.6），只存关节角度表达不了；
- `landmarks` 一节：每个 landmark 每帧相对静止位置的**平移**（毫米、Z 轴朝上）。实验室的运动数据里 landmark 只有平移（[03](03-asset.md) 第 7 节），所以这一版不存旋转。一节可以不写（没有 landmark 运动时）。代码里这一节的读取和校验由 T-09 加进 `trajectory.py`；
- 帧率、总帧数、来源（实验室控制器的哪一次输出）。

铰链只在场景描述里作为驱动源的可选说明。没有实验室轨迹时，T-06a 用铰链生成一条代用运动，再写成同样的每帧刚体变换，所以求解器只有一种输入形式。

### 5.3 回放包 `playback.json` + `playback.pc2`
已经实现，格式见 `src/asrp_core/playback.py` 开头的说明。表面网格以毫米存储，Blender 插件负责缩放显示。

### 5.4 溯源 `provenance.json`
每个输入文件（包括四面体网格）的哈希值、asrp 版本（git 提交号）、FEBio 版本、Python 版本、运行时间、运行命令、运行结果（成功或失败及原因）。

## 6. 物理后端接口

为了以后能换求解器、也为了把 Ziva 当作"参考后端"看待，物理计算被抽象成三件事：

1. **准备**：拿到场景描述，做好求解前的一切准备（读取已落盘的四面体网格、生成输入文件）；
2. **运行**：给定一段运动，计算每一帧；
3. **交结果**：按统一格式给出每帧每个顶点的位置。

FEBio 是第一个实现。Ziva 不在我们的软件里运行，它的结果由实验室在 Maya 里导出，按同样的"交结果"格式读入，用于对比。

## 7. 命令行（计划）

| 命令 | 作用 | 对应需求 |
|---|---|---|
| `asrp doctor` | 检查环境 | — （已有） |
| `asrp import-asset <导出文件夹> <输出文件夹>` | 导入资产，生成场景描述和检查报告 | R-01（已有，T-02） |
| `asrp check <scene.json> [<trajectory.json>]` | 检查场景设置；带上运动时，再查运动和场景对不对得上。有错误才失败，提醒照样通过 | R-02（已有，T-05） |
| `asrp run <scene.json> <trajectory.json>` | 运行一次，生成运行文件夹（已有，T-06a）；打印生成器报告、max\|u\|÷δ、三项检查和每帧用时，检查有不通过的就以 1 退出 | R-03、R-06 |
| `asrp run --feb <现成的 .feb>` | 替身模式：不生成输入，直接跑现成的 `.feb`，做运行文件夹、溯源、进度、取消、出错处理这层外壳（T-08）。生成器已接进上一行（T-06a） | R-03、R-06 |
| `asrp compare <运行文件夹> <Ziva 参考>` | 和 Ziva 对比 | R-05 |

Blender 插件的每个按钮都对应其中一条命令。界面能做的事，命令行都能做。

## 8. 一次运行的完整过程

1. 研究员在 Blender 里点"运行"；
2. 插件把场景描述和运动的路径交给 `asrp run`，在后台启动；
3. 核心程序新建运行文件夹，复制输入，记录溯源；
4. 校验场景，有错立即停止并报告；
5. 读取已落盘的四面体网格，并把它的哈希记进溯源记录（四面体网格在运行之前显式生成一次，不在这里重新生成，ADR-20）；
6. 生成 `model.feb`，调用 FEBio；
7. 插件定期读取进度（FEBio 日志里已完成的帧数）并显示；
8. FEBio 结束后检查是否"正常结束"，读出每帧结果；
9. 叠加 landmark 段；
10. 生成回放包；插件加载并在时间轴上播放。

## 9. 出错时怎么办

| 情况 | 系统的反应 |
|---|---|
| 场景设置有错（缺文件、单位不对、连接没有顶点） | 运行前就停下，用通俗的话说明是哪一项、怎么改 |
| FEBio 计算不收敛 | 停止，报告出错的帧号和 FEBio 的原始提示，**不显示任何结果** |
| FEBio 找不到 | 提示安装或设置 `ASRP_FEBIO` |
| 研究员取消 | 停止 FEBio，运行文件夹标记为"已取消" |
| 任何失败 | 运行文件夹保留，溯源记录写明失败原因，方便排查 |

**绝不在失败时显示上一次的旧结果。** 这是最容易误导研究的情况。

报告的帧号是 FEBio 自己的时间步编号（从 1 数）；取消有两种方式，在运行文件夹里新建一个名为 `cancel` 的空文件，或在终端按 Ctrl-C，两种都会结束 FEBio 的整个进程树。

## 10. 规模和性能

| 网格 | 顶点数 |
|---|---|
| 嘴唇 | 10,240（显示用）；计算用的四面体网格会粗一些 |
| 下颌、颅骨、牙齿 | 7 千到 2.8 万，**只作为刚体**，不参与有限元计算，不影响速度 |

速度主要取决于嘴唇四面体网格的大小和每帧子步数。S1 试验里 72 个计算点（有限元节点）、45 帧，用时约 0.3 秒（`uv run python spikes/s1_dynamic_jaw.py` 的输出）。T-04 定稿的嘴唇网格有 6,747 个计算点，只有重力的 15 帧本机 22 秒（11 的 A-18）。T-06a 实测：真实嘴唇（6,747 个计算点、1,428 根弹簧）51 帧的代用张嘴，FEBio 单线程 44.8 秒，0.90 秒/帧，没有重试（多线程是 27 秒，但结果不逐位重复，05 坑 17）；生成 `.feb` 4 秒、事后处理 2.6 秒。在暂定预算 2.5 秒/帧之内，暂时不用减子步或简化网格。速度要求来自正向推进（回放和钢琴界面的逐帧步进），不来自控制器训练：训练时不推进时间（ADR-30 及其修订）；暂定预算见 02 N-07。
