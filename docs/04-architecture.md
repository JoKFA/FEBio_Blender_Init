# 04 系统设计

这份文档说明软件分成哪几块、每块负责什么、数据怎么在它们之间流动。目标是：任何一个开发者只看这份文档和自己的任务卡，就知道自己写的东西放在哪、要和谁对接。

## 1. 总体结构

```
┌──────────────────── Blender ────────────────────┐
│  ASRP 插件（只管界面）                           │
│  导入资产 · 检查设置 · 运行 · 回放 · 对比          │
└───────────────┬─────────────────────▲───────────┘
                │ 调用命令行，传文件夹路径 │ 读取结果文件
                ▼                     │
┌──────────── asrp_core（独立程序）─────┴──────────┐
│  资产导入 → 场景描述 → 四面体化 → 生成 FEBio 输入   │
│  → 调用 FEBio → 读结果 → landmark 变形层          │
│  → 回放包 · 对比报告 · 溯源记录                   │
└───────────────┬─────────────────────▲───────────┘
                │ .feb 输入文件          │ 日志和结果
                ▼                     │
            ┌────────── FEBio ──────────┐
            │  有限元求解（不改它的代码）  │
            └───────────────────────────┘

所有输入、中间文件、结果都落在一个"运行文件夹"里。
```

三条基本原则：

1. **Blender 只管界面。** 插件里不写任何计算逻辑。插件崩了或者以后换成别的界面，计算部分完全不受影响。
2. **核心程序不依赖 Blender。** 可以单独在命令行里运行，以后实验室的控制器也通过它来调用物理计算。
3. **模块之间只通过文件交换数据。** 每一步的输入、输出都能单独打开检查，出了问题能定位到具体哪一步。

## 2. 两段计算

根据[资产分析](03-asset.md)第 4 节，最终的嘴唇形状由两段计算叠加而成，系统也按这两段来设计：

| 段 | 做什么 | 由谁算 | 输入 | 输出 |
|---|---|---|---|---|
| **物理段** | 下颌带动嘴唇，加上重力、惯性、组织之间的粘连 | FEBio | 场景描述 + 下颌运动 | 每帧"只有物理"的嘴唇形状 |
| **landmark 段** | 300 个 landmark 的蒙皮变形叠加在物理结果上 | 我们自己的代码（纯几何，不需要 FEBio） | 物理段的结果 + landmark 运动 + 蒙皮权重 | 每帧最终的嘴唇形状 |

分成两段的好处：和 Ziva 对比时，可以先单独比较物理段。差异出在物理还是出在 landmark 层，一眼就能看出来。

## 4. 运行文件夹

每次运行一个文件夹，放在 `runs/<运行编号>/` 下面，**里面的东西足以独立重现这次运行**：

```
runs/2026-11-03_neutral-to-AA_001/
  scene.json          场景描述（这次用到的全部设置）
  trajectory.json     这次的运动（每个驱动源每帧的刚体变换、landmark 每帧变换）
  meshes/             用到的网格（毫米、Z 轴朝上），包括已落盘的四面体网格（只读，哈希记在 provenance.json）
  model.feb           生成的 FEBio 输入
  model.log           FEBio 日志（包含每帧节点位置）
  physics/            物理段结果
  final/              叠加 landmark 段之后的结果
  playback.json       回放包（Blender 加载用）
  playback.pc2
  compare/            和 Ziva 对比的报告（如果做了对比）
  provenance.json     溯源记录
```

`runs/` 不进 git。`data/` 里提交的有 `lab_export/`、`preview/`、`briefing/`、`tetmesh/`（四面体网格是只读输入，ADR-19、ADR-20），其余不进。四面体网格是**显式生成一次、落盘并记哈希的输入**，运行时只读，不在运行中重新生成（fTetWild 同输入多次运行结果不同，见 ADR-20 和 [13](13-explanations.md) E-03）。需要分享某次运行时，把整个文件夹打包发送。

## 5. 主要文件的内容

格式细节（字段名、类型）写在代码的格式说明里：`src/asrp_core/scene.py`、`src/asrp_core/trajectory.py` 开头（T-05 定稿）。这里只规定**必须包含的信息**。

两条通用规则：
- **大数组不内嵌。** 网格、四面体网格、landmark 蒙皮权重都是被引用的文件，`scene.json` 里只写路径和 sha256。场景文件因此能用眼睛读，文件被改过也一查哈希就知道。
- **校验结果分"错误"和"提醒"。** 错误是算不了或会算错（缺文件、哈希不符、连接没有有效顶点……），`asrp check` 失败；提醒是能算、但缺了要补的东西（比如软组织还没有任何连接），`asrp check` 照样通过，提醒要写进导入的检查报告。

### 5.1 场景描述 `scene.json`

| 部分 | 必须包含 |
|---|---|
| 单位 | 固定为 mm、N、MPa、s；记录每个网格原来的变换、从原始资产换算过来的系数和坐标轴转换（顺序见 [03](03-asset.md) 第 10 节）。**几何单位和物理尺度分开**（ADR-22）：`units.mm_per_scene_unit`（几何，暂定 0.962，**必填**）；`units.physics_length_scale`（无量纲 k，**可以不写**，不写时取 1.0 并把来源标成"我们定的"）：求解器把模型当成几何尺寸的 k 倍大来算，几何和输出仍是毫米 |
| 软组织 | 名字、网格文件、原始 OBJ 的文件名和 sha256、四面体网格文件及其内容哈希、材料（类型和参数）、每个参数的来源（实验室设置 / Ziva 默认值 / 我们定的） |
| 骨头 | 名字、网格文件、原始 OBJ 的文件名和 sha256、质量、运动方式：**"固定"或"给定"**（ADR-21）。给定时写明**跟随哪个驱动源**，运动由 `trajectory.json` 里这个驱动源的每帧变换提供 |
| 驱动源 | 名字（实验室资产里就是关节名，比如 `jaw01`），以及可选的铰链说明（枢轴、转轴），用来生成代用运动和做检查。一个驱动源可以带动几块骨头：下颌和下牙都跟随 `jaw01`，和 Maya 里一个关节同时带动两块骨头一样（[03](03-asset.md) 第 4 节） |
| 连接 | 连接的两样东西、每个顶点的权重、刚度、类型。类型是 [05](05-ziva-to-febio.md) 第 3 节的两种做法：硬绑定（没有刚度）或弹簧（刚度 × 权重） |
| landmark | 名字、静止位置、对嘴唇顶点的蒙皮权重（被引用的文件） |
| 求解设置 | 帧率、每帧子步数、阻尼、重力、分析类型（动力学）。场景不记帧数：运动的帧率必须等于这里的帧率，帧数由 `trajectory.json` 给出 |
| 来源 | 从哪个资产文件、哪次导出生成的 |

### 5.2 运动 `trajectory.json`
- 每个驱动源，每一帧的 **4×4 刚体变换**（毫米、Z 轴朝上，包含平移和旋转，ADR-21），以驱动源的名字为键。跟随同一个驱动源的骨头都用这一份变换。骨头可平移也可旋转（论文 4.1.3），甩头实验里整个头在平移（4.4.6），只存关节角度表达不了；
- 每个 landmark 每帧的变换（平移和旋转）；
- 帧率、总帧数、来源（实验室控制器的哪一次输出）。

铰链只在场景描述里作为驱动源的可选说明。没有实验室轨迹时，T-06 第一版用铰链生成一条代用运动，再写成同样的每帧刚体变换，所以求解器只有一种输入形式。

### 5.3 回放包 `playback.json` + `playback.pc2`
已经实现，格式见 `src/asrp_core/playback.py` 开头的说明。表面网格以毫米存储，Blender 插件负责缩放显示。

### 5.4 溯源 `provenance.json`
每个输入文件（包括四面体网格）的哈希值、asrp 版本（git 提交号）、FEBio 版本、Python 版本、运行时间、运行命令、运行结果（成功或失败及原因）。

## 6. 物理后端接口

为了以后能换求解器、也为了把 Ziva 当作"参考后端"看待，物理计算被抽象成三件事：

1. **准备**：拿到场景描述，做好求解前的一切准备（读取已落盘的四面体网格、生成输入文件）；
2. **运行**：给定一段运动，计算每一帧；
3. **交结果**：按统一格式给出每帧每个顶点的位置。

FEBio 是第一个实现。Ziva 不在我们的软件里运行，它的结果由实验室在 Maya 里导出，按同样的"交结果"格式读入，用于对比。

## 7. 命令行（计划）

| 命令 | 作用 | 对应需求 |
|---|---|---|
| `asrp doctor` | 检查环境 | — （已有） |
| `asrp import-asset <导出文件夹> <输出文件夹>` | 导入资产，生成场景描述和检查报告 | R-01（已有，T-02） |
| `asrp check <scene.json> [<trajectory.json>]` | 检查场景设置；带上运动时，再查运动和场景对不对得上。有错误才失败，提醒照样通过 | R-02（已有，T-05） |
| `asrp run <scene.json> <trajectory.json>` | 运行一次，生成运行文件夹 | R-03、R-06 |
| `asrp compare <运行文件夹> <Ziva 参考>` | 和 Ziva 对比 | R-05 |

Blender 插件的每个按钮都对应其中一条命令。界面能做的事，命令行都能做。

## 8. 一次运行的完整过程

1. 研究员在 Blender 里点"运行"；
2. 插件把场景描述和运动的路径交给 `asrp run`，在后台启动；
3. 核心程序新建运行文件夹，复制输入，记录溯源；
4. 校验场景，有错立即停止并报告；
5. 读取已落盘的四面体网格，并把它的哈希记进溯源记录（四面体网格在运行之前显式生成一次，不在这里重新生成，ADR-20）；
6. 生成 `model.feb`，调用 FEBio；
7. 插件定期读取进度（FEBio 日志里已完成的帧数）并显示；
8. FEBio 结束后检查是否"正常结束"，读出每帧结果；
9. 叠加 landmark 段；
10. 生成回放包；插件加载并在时间轴上播放。

## 9. 出错时怎么办

| 情况 | 系统的反应 |
|---|---|
| 场景设置有错（缺文件、单位不对、连接没有顶点） | 运行前就停下，用通俗的话说明是哪一项、怎么改 |
| FEBio 计算不收敛 | 停止，报告出错的帧号和 FEBio 的原始提示，**不显示任何结果** |
| FEBio 找不到 | 提示安装或设置 `ASRP_FEBIO` |
| 研究员取消 | 停止 FEBio，运行文件夹标记为"已取消" |
| 任何失败 | 运行文件夹保留，溯源记录写明失败原因，方便排查 |

**绝不在失败时显示上一次的旧结果。** 这是最容易误导研究的情况。

## 10. 规模和性能

| 网格 | 顶点数 |
|---|---|
| 嘴唇 | 10,240（显示用）；计算用的四面体网格会粗一些 |
| 下颌、颅骨、牙齿 | 7 千到 2.8 万，**只作为刚体**，不参与有限元计算，不影响速度 |

速度主要取决于嘴唇四面体网格的大小和每帧子步数。S1 试验里 72 个计算点（有限元节点）、45 帧，用时约 0.3 秒（`uv run python spikes/s1_dynamic_jaw.py` 的输出）；嘴唇的计算点会多出两到三个数量级。要在四面体化任务（T-04）完成后实测，再决定是否需要减少子步数或简化网格。
