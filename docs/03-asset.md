## 2. 这个文件是什么

它是实验室**完整面部 Ziva 场景的精简版**。从文件名（"dev proxy jaw oor"，即"开发用的下颌 + 嘴唇代理场景"）和内容来看，实验室删掉了大部分肌肉的网格，只保留了下颌和嘴唇相关的部分。

但是 Ziva 自己的设置**大多还留在文件里**：

| Ziva 设置 | 数量 | 是什么 |
|---|---|---|
| zTissue | 41 | 软组织（会变形的部分） |
| zBone | 10 | 骨头（不变形，只跟着动） |
| zCloth | 2 | 布料式的薄层，其中一个是皮肤 |
| zAttachment | 140 | 两样东西之间的"粘连" |
| zMaterial | 43 | 材料参数 |
| zTet | 41 | 四面体网格的设置 |
| zFiber | 18 | 肌肉纤维方向（主动收缩用） |

41 个软组织里，有 34 个的原始网格已经被删掉了，但它们和求解器之间的连接还在。这一点很重要，见第 6 节和问题 Q7。

## 3. 原型要用的部分

顶点数和尺寸取的是**静止形状**，也就是 Maya 里名字以 `ShapeOrig` 结尾的那份网格，它是 Ziva 和蒙皮的输入。

尺寸有两种说法，一定要分清：
- **物体坐标**：网格自己记录的坐标；
- **场景坐标**（也叫世界坐标）：网格放进场景以后的坐标。五个网格都带着同一个"变换"：**放大 2.54 倍**，绕 X 轴转 -90°、绕 Z 轴转 180°，再整体下移约 75.4。Ziva 读的是场景坐标。

| 下颌 | `middleres_Jaw` | 骨头 zBone1，由下颌关节 `jaw01` 带动 | 7,426 | 196.8 / 146.5 / **155.9** |
| 颅骨 | `middleres_skull` | 骨头 zBone2 | 28,414 | 225.2 / 252.7 / 311.0 |

## 4. 运动是怎么传递的

从节点之间的连接关系，可以完整地还原出实验室场景里运动的传递路线（实验室源码也证实了没有别的路，第 13.2 节，ADR-29）：

```
① 下颌关节 jaw01 转动（控制器输出的一部分）
      │ 蒙皮（skinCluster1 带下颌、skinCluster2 带下牙）
      ▼
② 下颌骨和下牙跟着转（Ziva 骨头 zBone1、zBone4 读取它们的位置）
      │ 粘连（attachment）
      ▼
③ Ziva 计算软组织的变形：重力、惯性、被骨头和周围组织拉扯。输入是静止形状（ShapeOrig）
      │ zEmbedder 输出
      ▼
④ 叠加 landmark 关节的蒙皮：嘴唇 300 个（skinCluster7）；两眼各 300 个（skinCluster4、5）
      │
      ▼
⑤ 最终看到的嘴唇形状（控制器读的就是它）
      │ 包在它上面的曲线（wrap6、wrap7）
      ▼
⑥ 皮肤的显示形状再按这些曲线蒙皮一次（skinCluster13），也在物理之后
```

**关键结论：landmark 不参与物理计算，而是在物理结果上再叠一层变形（第④步）。进物理的只有下颌转动（第①步）。** 这和论文公式 22 的写法一致。对我们来说，FEBio 只需要算第③步；第④⑤⑥步是独立的、纯几何的计算。

## 6. 嘴唇被什么固定住

读粘连要注意两点：

- 每个粘连有"出发方"和"目标方"，**权重表记在出发方的顶点上**。出发方的这些顶点会被拉向目标方表面上离它最近的位置；
- 权重表里，**文件没存的元素取默认值 1.0**；根本没存权重表的粘连，等于出发方整块都粘着。推断：Maya 省略的元素等于默认值（但 `zAttachment2` 是整段显式存的，10,240 个里 76 个是 1.0，所以等于默认值的元素并不总被省略）。默认值 1.0 是**强推断**：全场景 21 个逐个元素存的权重表，存下来的值全是 0.0（没人会显式存几千个 0，除非 0 不是默认值）；下面上唇那 74 个没存的顶点贴着颅骨，和下唇 76 个存成 1.0 的顶点贴着下颌正好对称。待 Ziva 机器导出的 `ziva_maps.json` 里的 `default` 字段确认（A-33）。

全场景 140 个粘连里，21 个有没存的元素，23 个根本没存权重表。`tools/asset_report.py`（第 9 节）给每个粘连分开列"存下来的非零"和"按默认值算的"。

| 嘴唇连到 | 方向 | 粘连 | 权重大于 0 的顶点 | 怎么得出的 |
|---|---|---|---|---|
| 颅骨 | 嘴唇 → 颅骨 | `zAttachment1` | **74 个嘴唇顶点**（上唇） | 按默认值：存了 10,166 个，全是 0.0，没存的 74 个 |
| 下颌 | 嘴唇 → 下颌 | `zAttachment2` | 76 个嘴唇顶点（下唇） | 存下来的非零：整段存了 10,240 个，76 个是 1.0 |
| 两侧口角 node（zTissue4、zTissue5，各 254 个顶点） | 嘴唇 → 口角 | `zAttachment9`、`zAttachment10` | 348、309 个嘴唇顶点 | 存下来的非零 |
| 周围 6 块肌肉（网格已被删掉） | 肌肉 → 嘴唇 | 6 个 | 每块 32 到 52 个**肌肉的**顶点，粘在嘴唇表面上 | 存下来的非零 |
| 皮肤 | 皮肤 → 嘴唇 | 9 个 | 每个 36 到 516 个、合计 2,185 个**皮肤的**顶点，粘在嘴唇表面上 | 存下来的非零 |

嘴唇作为出发方、带粘连权重的顶点一共 **807 个**（不重复计数，占 10,240 个的 7.9%）：存下来的非零 733 个，按默认值 74 个。上唇、下唇、两侧嘴角这四组互不重叠。

**位置核对**（T-03：`tools/lip_attachments.py` 导出的四组，用 `data/lab_export/` 的 OBJ 量，由 `tests/test_lip_attachments.py` 断言；场景单位，Y 朝上；复现：`uv run python tools/lip_attachments.py --inventory E:/Codebase/asrp/data/asset_inventory.json`，再 `uv run python -m pytest tests/test_lip_attachments.py`）：74 个上唇顶点离颅骨最近顶点的距离中位数 3.28（最大 7.93），离下颌中位数 29.60（最大 33.83）；76 个下唇顶点正好反过来，离下颌中位数 3.28（最大 7.74），离颅骨中位数 29.10（最大 33.79）。两组重心一上一下，y 分别为 -70.56 和 -104.59，相差 34.03。着色截图 `data/preview/lip_attachments.png`。所以这 74 个就是贴着上颌骨的上唇顶点，和下唇挂下颌是对称的一对。

**嘴角经口角组织间接连到骨头**。沿粘连往外追（`tools/asset_report.py` 的"chain outward from the lip"一节；数字是权重大于 0 的出发方顶点数）：

```
嘴唇 zTissue1 ──348 / 309──▶ 左 / 右口角 node（zTissue4 / 5）
口角 node ──全部 254 个（没存权重表）──▶ zTissue2 / 3（各 1,364 个顶点，左右成对）
zTissue2 ──350──▶ 颅骨        zTissue2 ──512（按默认值）──▶ 下颌
zTissue3 ──394（按默认值）──▶ 颅骨    zTissue3 ──561（按默认值）──▶ 下颌
另外拉着口角 node 的：zTissue6 / 7（21 / 19 个顶点；它们自己有 13 / 9 个顶点连颅骨）、皮肤（86 / 53）
```

- node 就是口角：皮肤到它的粘连叫 `zAttachment115_left_node`、`zAttachment121_right_node`，论文 4.1.3 也提到嘴角处的 node 肌肉；
- node 自己**没有直接连骨头**，是经过 zTissue2/3 连上去的。zTissue2/3 左右成对、同时挂在颅骨和下颌上，最像颊肌，但网格已删，名字确认不了（推断，Q18）。zTissue6/7 是哪块肌肉也不知道。

**这意味着：** 上下唇各有一组直接连骨头的顶点，嘴角经两层组织连到颅骨和下颌，周围的肌肉和皮肤还粘在嘴唇表面上。第一阶段用哪几组、嘴角怎么近似，见 ADR-32。肌肉和皮肤粘在嘴唇表面的**哪些位置**，文件里没有直接记录，要用"离得最近的点"另外算；第一阶段不建这些粘连，所以不需要。

## 7. landmark 和运动轨迹

- 300 个 `oor_NN` landmark 都在文件里，挂在 `joint_oor` 下面；
- 文件里有 12,134 条动画曲线：12,120 条各有两个关键帧，分别在**第 0 帧和第 14 帧**；另外 14 条只有一个关键帧，在第 15 帧；
- **所有曲线的数值都不随时间变化。** 也就是说，文件里只有 landmark 和关节的**静止位置**，没有运动；

- 运动轨迹不在 `.mb` 里。实验室的钢琴界面运行时读 `combined_checkpoints.pkl`（在实验室网络盘的结果目录下），这个文件**不在源码仓库里**（`git -C <仓库> ls-tree -r --name-only HEAD` 里没有任何 `.pkl`），要另外向实验室要（D2）。

## 10. 单位和坐标轴（导入时必须处理）

**先套变换，再换单位，再转坐标轴。** 顺序固定，不能省：

1. **套用每个网格自己的变换**（放大 2.54 倍、旋转、平移），得到场景坐标。**这一步现在由 `tools/maya_export.py` 完成，导出的 OBJ 已经是场景坐标，导入时不能再套一次**（ADR-18）。每个网格的变换矩阵仍然写在 `mesh_report.json` 里，用来和 `.mb` 核对。场景里不同物体的放大倍数并不一样：解剖结构是 2.54，皮肤约 1.185，手约 6.28。所以**绝不能假设"所有东西同一个比例"**。
2. **换算长度单位**：1 个场景单位 = **0.962 mm**（`units.mm_per_scene_unit`）。论文附录 V 量的是"下颌宽 155.92 个单位，对应作者自己的 15 厘米"，而 155.92 正好是这个下颌在**场景坐标**下 z 方向的尺寸（第 3 节），所以 0.962 mm 对应的是场景坐标的单位。实验室控制器里也是这个数（9.62×10⁻⁴ m/单位，第 13.10 节）。z 在这个场景里是前后方向（左右是 196.8），和论文说的"宽"方向不一样，这只是低优先的疑问（Q3）。
   - 按这个换算，颅骨左右约 217 mm、前后约 299 mm，比一般成年人（宽约 140–150 mm）大约 1.5 倍，实验室会议也确认模型比真人大。**几何不改**；求解时按真人大小算，由物理尺度 k 处理（ADR-22、ADR-31，[05](05-ziva-to-febio.md) 第 2 节）。
3. **转坐标轴**：场景是 Y 轴朝上，脸朝 -Z 方向（已从场景确认，Q9）；Blender 和我们的计算是 Z 轴朝上。换算公式是 `(x, y, z) → (x, -z, y)`，转完以后脸朝 +Y 方向，写进检查报告。这是一次旋转，不是镜像，左右不会对调。

另外，**Ziva 求解器的缩放是 100**，含义未知；我们不再用 Ziva 的物理尺度（ADR-31），所以只是低优先的疑问（Q3）。

### 13.2 landmark 和物理的关系 ✅

- 四组 landmark（嘴唇 `oor_*`、两眼 `ooc_l_*` / `ooc_r_*`、额肌 `frontalis_*`，各 300 个）都**不进 Ziva**，是叠在 Ziva 结果之上的蒙皮。**证据强弱不同**：嘴唇和两眼有场景连线；额肌只有源码证据（它和眼周按同样的方式只移关节），v36 场景里没有它的蒙皮节点，连线查不了。场景连线：嘴唇静止形状 `middleres_OrbicularisOrisShapeOrig` 进 `zTet1`（Ziva 的输入是静止网格），`zEmbedder1` 的输出进 `skinCluster7`，再到最终形状；两眼同样（`zEmbedder1.og[18]` → `skinCluster4`，`og[19]` → `skinCluster5`）。最终的嘴唇形状只连到 `wrap6`、`wrap7` 和界面用的 blendShape，不回到 Ziva；
- **唯一进物理的是下颌**：`jaw01` → `skinCluster1` → 下颌网格 → `zBone1`；
- 140 个粘连的两端全是 Ziva 物体，没有关节；脚本也不改 Ziva 的静止形状（`UI:565-602` 的重置技巧被 `if False` 关掉了，`UI:4457`）；
- 皮肤的显示形状由包在最终嘴唇上的曲线带动（`skinCluster13`），也在物理之后（论文附录 I 的"分层线变形"）；
- 下颌怎么驱动：训练环境三个轴都转（`ENV:1855`）；钢琴界面只转俯仰并打关键帧（`UI:1343-1360`）；下牙和舌头的显示网格另外多转 0.25（`teeth_correction_weight`，`UI:278`、`UI:1367-1388`），注释说是因为嘴唇被拉得比刚性牙齿远；
- 控制器读的网格：训练时读 `middleres_OrbicularisOris` 的世界坐标（`ENV:4279-4297`），也就是**物理 + landmark 蒙皮之后**的最终形状；界面优先读 `*_RENDER` 代理网格，它用 blendShape 跟着实时的 Ziva 网格（`UI:526`、`UI:640-654`）。

### 13.3 控制器优化时物理不在环 🔶（训练时不推进时间 ✅；同一帧会不会重新求解 ❓，Q20）

- 训练环境打开场景时，把第 0 到 14 帧走一遍（重力沉降，`ENV:1084-1102`）。这是唯一推进时间的地方；
- 之后每一步：限速 → 转 `jaw01` → 把 landmark 移到绝对位置 → 读网格 → 算距离和奖励（`ENV:1224`、`1855`、`1899-1931`、`2256-2261`），中间不推进时间。🔍 所以每一步读到的嘴唇 = 第 14 帧的 Ziva 结果 + landmark 蒙皮；同一帧里下颌转了以后 Ziva 会不会重新求解，源码证明不了（Q20，高优先，和 Q17 联动：Q17 的推断假设不重新求解）；
- 梯度来自 LBS 代理（`LBS:8-122`、`EVAL:1577-1729`）：函数值用 Maya 实际读到的顶点位置，梯度只用 LBS 的雅可比（`LBS:117-120`）。目标 = 0.34 × 归一化距离 + 0.33 × 应变能 + 0.33 × Hill 肌肉功（`EVAL:210-212`）；
- 四种组织都走解析梯度，名字不认识时才走旧路径（`EVAL:2172-2203`）。🔍 推断：旧的数值梯度扰动的是顶点坐标本身，从不调 Maya（`EVAL:1746-2160`）。
- 演示录像里的钢琴界面则是每一步都向前推进物理：Script Editor 里每行 `Timestep completed; stepped to frame N`，相邻行间隔约 2.3–2.5 秒，状态栏一行写 `stepped to frame 36.0; wall clock time 1.519s`（[14](14-ziva-demo-walkthrough.md) 第 2 节，14:46，演示机，把握中）。所以"物理不在环"只对训练成立；界面逐帧步进，将来的速度要求来自这里（ADR-30 的修订，02 N-07）。

### 13.4 Hill 肌肉模型 ✅

- 位置：`EVAL:1612-1665`（正在用的 torch 版），`LBS:212-247` 有同样一份；
- 公式：F = min(a·F_len·F_vel + F_PEE + F_SEE, F_max)，F_len 是高斯型长度曲线，F_vel 是 Hill 1938 的双曲线（`EVAL:1638-1656`）。参数都是常数，注释写"empirical value"：激活 a = 0.8，F_max = 17/300 N（整片嘴唇 17 N），原长 2 cm 等；
- 简化：每个 landmark 的力一样；长度用"整张网格到目标的剩余距离 ÷ 300"代替，不是每块肌肉的实际长度；速度是常数；
- 用在哪：作为目标函数的第三项（权重 0.33），**只影响控制器的梯度，从不写回 Ziva**；
- 物理层里的主动收缩：脚本把 `zFiber1`、`zFiber2` 的 `excitation` 设成 0 并打关键帧（例如 `b99-frame1to4-get-b1to3/d2 helper functions/d2-adhoc-for-b99-part2-generate-mb-use-V3.py:656-678`）。

新系统怎么回应，见 ADR-33。

### 13.6 实验室实际用到的 Maya / Ziva 功能 ✅

替换时要覆盖的面很小：

- **Ziva 命令**只有 `cmds.ziva(s=True)`（选中求解器），共 4 处，返回值只用来打印。没有创建组织、骨头、粘连、材料、缓存，也没有 zBuilder 调用；
- **Ziva 属性**：给 `zSolver1.startFrame`、`zSolverShape.enable` 打关键帧或复位（`UI:582-599`、`UI:4784-4790`）；初始化（第 0 到 14 帧）时把 `substeps` / `maxNewtonIterations` 临时设成 **1 / 2**，之后恢复，注释说"全质量"是 **2 / 5**，太慢（`UIc:3817-3838`）；`zFiber*.excitation` 设成 0；碰撞设成 0（`AUTO/disable_collisions.py:145-148`）；

### 13.9 实验看的是物理层的什么输出 ✅

**只看顶点位置**（世界坐标）。全仓库没有从 Ziva 读过能量、力、应力或体积。所有"能量"和"力"都是脚本拿顶点位置自己算的：应变能（`ENV:2328-2504`）、力和力矩（对顶点轨迹做差分，假设质量 1 kg）、速度（逐帧位移）、体积（由网格算）。所以新物理层第一版只要能逐帧输出各网格的顶点，就覆盖了实验室现有的全部分析脚本。
