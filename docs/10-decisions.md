# 10 决策记录

项目里做过的关键决定都记在这里。每条写清楚：**定了什么、为什么、放弃了什么**。以后有人问"为什么不用 X"，先查这里。

要推翻一条已定的决策，新增一条记录说明原因，并把旧的那条标记为"已被 ADR-xx 取代"，不要直接删改旧记录。

状态：✅ 已定；⏳ 待定（链接到 [11](11-risks-and-questions.md) 的待决问题）。

---

### ADR-01 物理计算用 FEBio ✅ 2026-10-27
- **决定**：用 FEBio 替换 Ziva。以后如果需要第二个求解器做交叉验证，首选 ArtiSynth。
- **原因**：FEBio 专为生物力学开发，有已发表的验证；源码开源（MIT 许可），每一步计算都能检查；输入输出都是文件，适合独立运行；自带刚体、动力学和多种软组织材料。
- **放弃了**：AdonisFX、Houdini Otis（闭源，没有生物力学方面的有效性声明，本质上和 Ziva 是同一类工具）；SOFA、PolyFEM（在 Windows 上安装风险高）；自己写有限元（验证工作量太大）。
- **附注**：官方安装包的许可只允许单机安装和内部使用，不允许再分发（已读安装附带的许可协议）。

### ADR-02 操作和显示用 Blender ✅ 2026-10-27
- **决定**：用 Blender 替换 Maya 作为操作界面。
- **原因**：免费开源，Python 接口完整，任何人都能装；Ziva 停售以后，Maya 对这个项目已经没有不可替代的价值。
- **放弃了**：继续用 Maya（许可费用，而且原来就是因为 Ziva 才绑定在 Maya 上）。
- **附注**：核心程序不依赖 Blender，以后需要的话可以再加 Maya 界面。

### ADR-03 求解在独立程序里运行，靠文件交换数据 ✅ 2026-10-27
- **决定**：Blender 插件只管界面，所有计算在独立的核心程序里，两者通过运行文件夹里的文件交换数据。
- **原因**：求解崩溃不影响 Blender；不开 Blender 也能批量运行，以后控制器也能直接调用；每一步的输入输出都能单独检查和重算。
- **证据**：`tools/check_blender_addon.py` 验证了 Blender → 子进程 → 核心程序 → 结果返回这条链路。

### ADR-04 单位统一为毫米、牛顿、兆帕、秒 ✅ 2026-10-27
- **决定**：导入时换算一次，之后全部用这一套。
- **原因**：生物力学常用的单位组合，数值大小合适；只换算一次，可以避免多处换算导致的错误。

### ADR-05 用动力学分析，不用准静态 ✅ 2026-10-28
- **决定**：按时间逐帧推进，考虑惯性。
- **原因**：实验室的流程有重力沉降（第 0 到 14 帧）和甩头时的惯性效果；Ziva 本身就是逐帧推进的。
- **取代**：最初计划用准静态（更简单、更稳定），看过论文和资产以后改了。

### ADR-06 原型直接用实验室资产 ✅ 2026-10-29
- **决定**：不自己建模下颌和嘴唇，直接用实验室提供的 Maya 场景。
- **原因**：结果能直接和实验室的 Ziva 结果对比；不需要额外的建模工作。

### ADR-07 产品用的数据一律来自实验室导出的开放格式；.mb 只用来核对 ✅ 2026-10-29（"谁来导出"已被 ADR-18 取代）
- **决定**：网格由实验室导出成 OBJ（或 FBX、Alembic），Ziva 设置导出成属性清单，蒙皮权重导出成权重文件。我们从 `.mb` 里读出的东西（结构、顶点坐标、权重）**只用来核对**这些导出，不作为产品的数据来源。
- **原因**：`.mb` 的格式没有公开文档。顶点坐标和大部分属性我们读出来了，但网格的"面"读不出来，还有 41 个数据块的格式没认出来。产品不能建立在猜出来的格式上，Maya 版本一换就可能失效。
- **更正**：本条的早期版本说"下颌有 3 个坏点、颅骨有 14,204 个坏点"，那是读错了顶点数（把坐标数值的个数当成了顶点数）造成的，按正确的读法没有坏点。
- **放弃了**：继续破解 `.mb` 的网格编码。

### ADR-08 landmark 作为物理计算之后的一层蒙皮变形 ✅（待实验室确认）2026-10-29
- **决定**：FEBio 只算物理（下颌带动、重力、粘连），landmark 的变形在物理结果之后单独叠加。
- **原因**：资产里的连接关系显示，Ziva 的输出进入 skinCluster7，再由 300 个 landmark 关节变形（[03](03-asset.md) 第 4 节）；论文公式 22 也是纯蒙皮公式。
- **风险**：如果实验室确认 landmark 实际上参与了物理计算，物理段的设计要改。所以把它列为问题 Q1，**在 T-06 第二版开工前确认**（第一版只算下颌带动和重力，不受这个问题影响）。

### ADR-09 结果回放用"表面网格 + 点缓存" ✅ 2026-10-28
- **决定**：结果打包成表面网格加每帧点位置文件（PC2 格式），由 Blender 自带的 Mesh Cache 修改器播放。
- **原因**：Blender 原生支持，不需要每帧重建网格；数据保持毫米，只缩放显示。
- **证据**：`tools/check_playback.py`，逐帧误差小于 0.000001 mm。

### ADR-10 写入 FEBio 时重力反号 ✅ 2026-10-27
- **决定**：写进 FEBio 的重力（作用在整个体积上的力）取"物理方向的相反数"。
- **原因**：实测 FEBio 4.13 中，填 -9810 反而往上推，和按手册第 3.13.3 节公式推出的方向相反（[05](05-ziva-to-febio.md) 坑 1）。
- **守护**：S1 的"组织应该往下沉"检查，每次自动检查都会跑。

### ADR-11 FEBio 一律加 -noconfig 运行 ✅ 2026-10-27
- **原因**：避免每台电脑上的个人配置影响结果，保证可复现。

### ADR-12 以文档为唯一依据协作 ✅ 2026-10-29
- **决定**：这套文档是项目的唯一依据。改设计先改文档；任务通过任务卡分配；人和 AI 开发会话遵守同样的规范。
- **原因**：项目会有多人参与，大家需要一个共同的、可以查证的依据，而不是靠聊天记录。

### ADR-13 原型的物理范围 ⏳
- 待定，见 [11](11-risks-and-questions.md) 的 P-01。目前的推荐是：第一阶段用方案 A（按区域挂到骨头上），第二阶段用方案 B（加上相连的组织）。方案 D（用 Ziva 结果当边界）随 ADR-17 放弃。实验室认可挂法后在这里补全。

### ADR-14 代码托管平台 ✅ 2026-10-29
- **决定**：GitHub 私有仓库 `JoKFA/FEBio_Blender_Init`，只邀请项目成员。
- **原因**：文档里有未发表论文里的数字，仓库必须保持私有（N-06）。
- **还没做**：`main` 分支保护、邀请成员，由 T-16 落实。默认合并请求模板已加（2026-10-30）。

### ADR-16 导入顺序固定为：先套变换，再换单位，再转坐标轴 ✅ 2026-10-29（第一步由 ADR-18 移到导出时）
- **决定**：每个网格先套用它自己在 Maya 里的变换得到场景坐标，再乘长度换算系数，最后从 Y 朝上转成 Z 朝上。
- **原因**：实验室的骨骼和嘴唇网格都带着放大 2.54 倍和旋转，场景里不同物体的放大倍数还不一样（[03](03-asset.md) 第 10 节）。论文的单位换算对应的是场景坐标（下颌 155.92 吻合）。顺序一错，尺寸和方向就全错，而且不会报错。
- **守护**：T-02 的验收检查"下颌在场景坐标下 z 方向为 155.92"。
- **更新**：顺序不变，但第一步（套变换）现在在导出时完成，见 ADR-18。

### ADR-15 复现的标准是"坐标一致"，不是"文件一致" ✅ 2026-10-29
- **决定**：判断两次运行是否相同，比较解析出的每帧坐标（差别 ≤ 1×10⁻⁹ mm）和回放文件，不比较 FEBio 的原始日志。
- **原因**：实测同一模型跑两次，日志不同（里面有时间戳），坐标最大差 1×10⁻¹³ mm，回放文件逐位相同（11 的 A-24）。

### ADR-17 目标是"实验室能继续做研究"，不是复刻 Ziva ✅ 2026-10-29
- **决定**：第一阶段不设"和 Ziva 差几毫米以内"的数值合格线。合格与否看三样东西：
  1. 自动检查和真实资产上的合理性检查都通过；
  2. 研究员把 Ziva 和 FEBio 的结果并排看，按固定的几个问题评审，没有"不能接受"的项；
  3. 和 Ziva 的差别照常算出来写进报告，但只作参考。

  具体做法见 [07](07-validation.md) 第 3、4 节。
- **原因**：
  - 实验室的研究成果是控制器，物理层只要能让控制器继续工作、结果看起来合理就够了；
  - Ziva 的材料参数很可能全是默认值（A-22），本身不是"正确答案"；
  - 两个求解器的材料公式和时间积分方法不同，要逐点对上 Ziva，需要大量的标定工作，结果还不确定，花在这上面不值得；
  - Ziva 停售以后，实验室的新模型要直接在新系统里搭建，从 Ziva 导入只是一次性的迁移。
- **放弃了**：
  - P-01 的方案 D：它只是为了让逐点对比更公平，还有两个没解决的技术问题；
  - P-02 的数值容差；
  - "调参直到进入容差"的标定任务。T-12 改成有时间上限的参数调整。
- **仍然保留**：
  - 尽快向实验室要 Ziva 参考结果，因为许可到期以后就再也做不出来了；
  - landmark 层和 Ziva 的精确对比（T-09）。那是同一个公式，结果应该一样。

### ADR-18 本机 Maya 只作迁移工具；Ziva 机器只做离不开 Ziva 的事 ✅ 2026-10-30
- **决定**：
  1. 开发机装 Maya 教育版（现在是 2027），用 `tools/maya_export.py` 从实验室给的非 Ziva 版场景导出网格、landmark 权重和关节；
  2. **产品不依赖 Maya**（ADR-02 不变）。Maya 只用于一次性迁移，`tools/verify.py` 也不需要它；
  3. OBJ 文件由我们的脚本直接写，不用 Maya 的 OBJ 插件。坐标就是场景坐标，所以 ADR-16 的第一步在导出时完成，T-02 只做换单位和转坐标轴，**不能再套一次变换**；
  4. 只有 Ziva 设置、Ziva 参考结果和运动这三项用 Ziva 机器，用 `tools/ziva_machine_export.py` 一次做完（[12](12-lab-export-checklist.md) 第二部分）。两份 Ziva 结果来自**同一次解算**：脚本临时接一个网格到 `skinCluster7` 的输入上，AbcExport 一次写两个文件，不切换 `envelope`。这样省一次解算，T-09 的精确对比也不用依赖 Ziva 两次解算逐帧相同。
- **原因**：
  - 实验室反馈 Ziva 机器大约 4 个人轮流用，清单里只有一小部分真正需要 Ziva；
  - 导出脚本原来没运行过，现在能在本机反复运行和修改；
  - 导出变成仓库里能重复运行、带核对的工具，不是一次手工操作；
  - 文档原来的导出脚本用 Maya 的 OBJ 插件，按 Autodesk 公开的示例源码，它写的是场景坐标，而 T-02 又要求再套一次变换，会放大两次。自己写文件，坐标含义就由我们决定。
- **证据**（2026-10-30）：
  - `tools/maya_export.py` 40 秒内导出全部文件，自检通过；
  - `tools/check_lab_export.py` 不经过 Maya，直接从 `.mb` 读顶点，和导出文件逐点比较，5 个网格最大差别小于 0.0000001 个场景单位，新旧两个 `.mb` 都一样。这条证明顶点和顺序对；变换矩阵来自 Maya 自己的报告，它的独立检查是从 OBJ 量出的下颌尺寸 155.92；
  - 反向试验可以重复运行：`tools/check_lab_export.py --self-test`。调换两个嘴唇顶点，差别 62.35；真的多套一次变换，下颌 z 尺寸变成 372.16；删掉一半嘴唇的面，出现 128 条开口的边。三种都失败；
  - `tools/rehearse_ziva_export.py` 在普通 Maya 上排练 Ziva 脚本，结果写在 `data/ziva_rehearsal/rehearsal_report.json`。
- **放弃了**：全部请实验室操作；继续破解 `.mb` 的网格编码。
- **注意**：教育版只能用于学习和研究，不能商用；**绝不在教育版 Maya 里保存实验室的 `.mb`**，否则文件会被打上教育版标记。脚本只读不存。

### ADR-19 私有仓库可以存放派生数据 ✅ 2026-10-30
- **决定**（项目负责人定）：仓库是私有的，所以我们导出和派生的文件、团队内部材料可以提交。现在提交的是 `data/lab_export/`（网格、权重、关节）、`data/preview/`（Blender 预览）、`data/briefing/`（讲解页）。**实验室的原始 `.mb`、论文和演示视频仍然绝不提交。**
- **原因**：T-02、T-04、T-06 要用导出数据，克隆下来就能开工，不用再单独传文件；讲解页和预览也跟着仓库走。
- **不提交的**：`assets/`、`runs/`，以及体积大而且能重新生成的 `data/asset_inventory*.json`、`data/ziva_rehearsal/`。`.gitignore` 还会拦住任何位置的 `.mb`、`.ma`、`.pdf`、`.mp4`。
- **注意**：
  - 这些派生文件含有完整的网格和权重，等于资产的另一种格式。所以仓库必须保持私有、只邀请项目成员，也不发到仓库以外的地方；
  - 资产的使用许可（Q6）还没有答复。如果实验室有限制，要把这些文件从 git 历史里清掉，光删除文件不够；
  - T-03、`tools/check_lab_export.py` 和重新构建讲解页仍然需要本地有 `.mb`。
- **取代**：N-06 和 03 第 11 节里"派生数据不进仓库"的部分。
